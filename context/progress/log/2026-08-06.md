## 런타임 구현 구조 결정 (Codex, Ubuntu)

- Jetson·로봇 전에 B·C·D와 전체 사용자 흐름을 최대한 개발하기로 함.
- 기존 GaP 2Hz 판단 루프를 세션 전체를 관리하는 이벤트 기반 상태 머신으로 확장. UI·Pose·로봇·촬영
  결과는 단일 `asyncio.Queue`로 전달하고 `Coordinator`만 상태를 변경.
- 기본 배포는 Python 프로세스 하나로 유지하고, ROS 2는 phorce 모션/피드백 경계에서만 사용.
- 기능을 줄이지 않되 과설계를 피하기 위해 초기 코드는 8개 내외의 책임별 모듈로 시작. Robot·Capture·
  Camera/Pose처럼 실제 교체가 필요한 경계만 작은 인터페이스로 격리.
- `dev` 설정에서는 `FakeRobot`, `FakeCapture`, 노트북 카메라/녹화 영상으로 구도 선택→가이드→정렬→
  촬영→리뷰→재촬영/확정 전체 흐름을 검증하고, `jetson` 설정에서 실제 구현체로 교체.
- 상세 설계 문서 추가: [`../../knowledge/architecture/runtime-architecture.md`](../../knowledge/architecture/runtime-architecture.md).
- 공통 구현 작업을 [`../../work/00-runtime-foundation/`](../../work/00-runtime-foundation/) 트랙으로 추가.

## VLM 확장 전략 결정

- 먼저 VLM 없는 `LocalVerifier`로 전체 구도 선택→정렬→촬영 흐름을 완성하기로 함.
- 상태 머신의 기존 `VERIFYING`을 확장 지점으로 사용하고, 이후 `VlmVerifier`를 같은 인터페이스에 선택적으로
  연결. 상태 머신·웹·촬영 모듈은 변경하지 않음.
- VLM은 정렬 완료 후보 프레임 한 장에만 1회 호출하고 실시간 Pose 루프에는 넣지 않음.
- 실제 API 연결 전 fake로 성공·구도 거절·타임아웃 세 경로를 준비.
- VLM 타임아웃·네트워크/API 오류 시 로컬 검증 결과로 진행하는 `fail_open` 정책으로 기본 촬영 경로 보호.

## 트랙 C — 엔드이펙터 폰 원격 셔터 확정 (Claude Code)

- 안드로이드 IP Webcam(경로 1)은 됐지만 화질이 기대 이하, 아이폰 Shortcuts+Pushcut(경로 3)은 화질은

- 원래 세 경로에 없던 네 번째 방식을 즉석에서 검증: 아이폰이 Jetson의 HTTPS 페이지를 Safari로 열고
  `getUserMedia`로 카메라 스트림을 상시 유지, Jetson은 WebSocket으로 붙어 있다가 `"capture"` 메시지
  한 번으로 무음 원격 트리거 → 그 순간 프레임을 JPEG로 되돌려받음. iOS는 카메라 API를 HTTPS(또는
  localhost)에서만 허용해서 자체서명 인증서(`certs/`)를 폰에서 1회 수락하는 절차가 필요했음.
- 검증: 단발 트리거 성공 후 연속 3회 성공, 이어서 15초 안에 30회 연속 트리거(약 2Hz)도 파일
  충돌·유실 없이 전부 성공(저장 파일명에 마이크로초를 넣어 동시간대 충돌 버그를 먼저 수정함).
- `../../knowledge/decisions.md` 확정 표로 이동, `work/C-eef-camera-shutter/README.md`에 경로 4로
  기록하고 최종 API 스펙(`GET /`, `WS /ws`, `POST /trigger`) 채움. 구현은
  `scripts/phone_capture_server.py` + `web/phone_capture.html`.

## 트랙 C 실연동 + 트랙 B 최소 인식 (Claude Code)

새 8단계 사용자 시나리오(`../../knowledge/scenario-walkthrough.md`)를 로컬에서 데모하기 위해(RViz
로봇 + 브라우저 탭=iPad + 노트북 웹캠=C270 + 아이폰) 두 가지를 병행 진행. 프런트엔드 목업(iPad1/iPad2
화면을 8단계에 맞게 다시 그리는 작업)은 Codex에게 별도로 위임하고, 이 세션에서는 겹치지 않는 백엔드
쪽만 작업.

**트랙 C 실연동**: `geekseek.capture.WebAppCapture` 추가 — `web.py`의 `/phone`(페이지),
`/phone-ws`(폰 연결 유지), `/photos`(정적 서빙)에 바인딩되어 `Coordinator._capture()`가 호출하는
`CaptureDevice.capture()`를 실제로 구현. `config/local-demo.yaml`(robot: rviz, capture: webapp, web에
`certs/`의 자체서명 인증서)로 켤 수 있음. 실제 아이폰 + RViz robot으로 구도 선택 → 로봇 이동 → 정렬 →
검증 → **실제 촬영** → 리뷰까지 전체 상태 머신 왕복을 확인(`photos/phone_1.jpg` 저장, `/photos/`로
서빙 확인). `scripts/phone_capture_server.py`(독립 테스트용)도 라우트명(`/ws`→`/phone-ws`)을 맞춰서
계속 단독 실행 가능하게 유지.

**트랙 B 최소 인식**: `src/geekseek/perception.py` 신설. `MediaPipePersonSensor`가 MediaPipe Pose
Landmarker(`models/pose_landmarker_lite.task`, IMAGE 모드, pip 설치+모델 다운로드 완료)로 프레임 한
장에서 `PersonSignal(detected, size_ratio, center_x, center_y)`을 뽑고, `is_approaching()`/
`is_positioned()`로 시나리오 2단계·4→5단계에 대응하는 임계값 판단을 제공. `FakePersonSensor`는 기존
fake/real 분리 패턴을 그대로 따름. 처음 노트북 웹캠으로 검증했을 때 사람이 없어도 낮은 신뢰도 관절점이
화면 밖으로 튀어 size_ratio가 1.8까지 나오는 버그를 발견 — `visibility` 기준으로 관절점을 거르고
좌표를 [0,1]로 clamp해서 수정. 수정 후 `scripts/test_webcam_perception.py`로 145프레임 연속 정상
감지(size_ratio 0.13~0.22, center 안정) 확인. 아직 워크플로 상태 머신에는 연결 안 함 — 어디에 어떻게
연결할지는 별도 결정 필요(`../../progress/STATUS.md` "다음 체크인" 참고).

의존성 추가: `httpx`를 dev→core로 이동(이미 완료), `mediapipe`, `opencv-python`을 core 의존성에 추가.
모델 파일(`models/pose_landmarker_lite.task`, 5.7MB)은 STEP/STL과 같은 방식으로 리포에 커밋(현장
네트워크 리스크 대비).
