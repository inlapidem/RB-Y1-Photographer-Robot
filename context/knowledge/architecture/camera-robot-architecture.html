phorce SDK 문서(퀵가이드·튜토리얼·매뉴얼·studio·pcm)와 팀 아이디어를 맞춰본 결과를 바탕으로, 실제로 손에 쥔 하드웨어에서 돌아가는 소프트웨어 구조를 다시 짠 문서입니다.

1먼저 — SDK가 실제로 허용하는 것

원래 제안서는 임피던스 제어·직접교시·잔차보정을 실시간 코드로 구현하는 걸 전제로 했는데, 해커톤 SDK 문서를 읽어보니 참가자 코드가 만질 수 있는 표면이 그보다 훨씬 좁습니다. 이걸 먼저 인정하고 설계해야 현장에서 안 되는 걸 붙잡고 시간을 버리지 않습니다.

가장 중요한 제약

Jetson 코드가 로봇팔에 할 수 있는 일은 딱 두 가지뿐입니다 — /phorce/feedback으로 12축 상태를 1kHz로 읽기, 그리고 미리 저장된 모션 슬롯 번호(1~50) 하나를 재생. 관절 목표위치·피드포워드토크·Kp·Kd를 실시간으로 넣는 저수준 명령은 매뉴얼에 "참가자 API가 아님(의도적 비공개)"으로 명시돼 있습니다. 즉 실시간 임피던스 제어·연속 시각 서보잉·ASAP 잔차보정은 실물에서 이번 대회 범위 밖입니다.

그런데 오히려 잘 맞는 부분

"직접교시"는 실시간 코드가 아니라 phorce Studio라는 별도 GUI로 합니다 — 서보를 끄고 손으로 로봇을 움직이면 pcm이 1kHz로 궤적을 기록해 SD카드에 슬롯으로 저장합니다. 그리고 원래 제안서의 GaP 스킬 그래프·DREAM-Chunk(검증된 동작 사전) 개념은 "이산적인 동작 번호를 상황에 맞춰 고른다"는 이 SDK의 모델과 정확히 같은 모양입니다. 그러니 그 두 아이디어를 설계의 중심으로 그대로 가져가면 됩니다.

추가 공지로 확인된 것 — P-Vector

운영진이 추가로 공유한 자료(해커톤_추가공지_p_vector.pdf)를 보면, 모션 슬롯의 실체인 MotionMap.csv는 각 축마다 P(i) = [yd, Ltraj, s0, sd](목표각도·구간시간·가속·감속) 키프레임을 이어 붙인 5차 다항식 궤적 표입니다. 즉 손으로 가르치는 것 말고, 이 포맷대로 CSV를 직접 계산해서 만드는 "프로그래밍 방식 모션 저작"도 가능합니다 — 여전히 사전 저작 단계일 뿐 실시간 스트리밍은 아니지만, 팬/틸트처럼 정밀한 타이밍이 필요한 움직임엔 손교시보다 이쪽이 낫습니다. 자세한 포맷은 §6-1 참조.

현장 팁

Studio의 교시 화면은 저장 전 화면에서 미리보기가 되고, 저장 후 로봇에서 재생까지 앱 안에서 다 됩니다. 그러니 슬롯 라이브러리를 하루 전에 다 가르쳐 놓고, 무대에서는 새 구도 하나를 즉석에서 추가 교시하는 순간을 라이브 데모로 넣으면(그리고 바로 Jetson 판단 루프가 그걸 골라 재생하는 걸 보여주면) "직접교시"를 실제로 보여주면서도 SDK 제약 안에서 완전히 정직한 시연이 됩니다.

6-1. 대안: P-Vector를 직접 계산해서 슬롯 만들기

손교시는 사람 손 떨림이 그대로 들어가고, 재현하려면 다시 손으로 잡고 움직여야 합니다. 팬/틸트 스윕처럼 "정확히 몇 초에 몇 도, 얼마나 부드럽게"가 중요한 카메라 무빙은 좌표를 계산해서 MotionMap.csv를 직접 쓰는 편이 낫습니다 — 조정도 숫자만 바꾸면 되니 반복 튜닝이 훨씬 빠릅니다.

필드의미범위 / 형식
yd이 구간이 끝날 때의 목표 각도(output축 기준)-360~360°, int16
Ltraj이 구간의 궤적 길이(진행 스텝 수 → 사실상 소요 시간)정수
s0 / sd구간 시작/종료 시 가속·감속 형태(무차원). 시작·끝 속도는 항상 0으로 묶이는 5차 다항식이라, 이 값으로 "얼마나 급하게 붙었다 떼는지"만 조절-128~128, int8

모션 하나(MS)는 이런 구간(MD)을 여러 개 이어 붙인 표입니다. 축마다 열이 하나씩 있고, 그 축이 이번 구간에서 안 움직이면 -로 비워둡니다.

# 예: "왼쪽으로 30도 천천히 팬" 한 구간을 pan 축에만 넣고 나머지는 정지
def pan_sweep_keyframe(current_deg, target_deg, duration_ms, ease=10):
    return {
        "pan":  [target_deg, duration_ms, ease, ease],  # [yd, Ltraj, s0, sd]
        "tilt": "-",
        "roll": "-",
        # ... 나머지 축도 전부 "-"
    }

주의할 점

손교시는 저장 후 Studio가 다시 읽어서 검증까지 해주지만, CSV를 직접 써 넣는 경로는 그런 안전망이 없습니다. 잘못된 값(범위 초과, 축 개수 불일치)이 그대로 SD카드에 올라갈 수 있으니 ① --target sim:demo로 먼저 재생해보고, ② 실물 재생 전엔 항상 Studio로 다시 열어 그래프가 정상인지 눈으로 확인한 뒤 재생하세요.

7접촉/이상 감지 — current_a / dob_a 기반

실시간 순응은 못 하지만, "지금 뭔가에 부딪혔다"는 감지는 피드백 필드만으로 충분히 됩니다. 각 축의 평상시 전류·외란추정 기준선을 만들어두고, 재생 중 그 기준선을 벗어나면 이상으로 판단합니다.

# 피드백 콜백 안 — 저장만
def on_feedback(fb):
    for i, axis in enumerate(fb.axis):
        if axis.valid:
            baseline[i].update(axis.dob_a)   # 이동평균/표준편차 갱신
            latest[i] = axis

# 상태/안전 확인 타이머 안 — 실제 비교와 반응은 여기서
def check_contact():
    for i, axis in enumerate(latest):
        if axis is None:
            continue
        if abs(axis.dob_a - baseline[i].mean) > CONTACT_SIGMA * baseline[i].std:
            return i  # 이 축에서 이상 감지
    return None

# 슬롯 선택 직후
contact_axis = check_contact()
if contact_axis is not None:
    robot.cancel_current()          # 가능하면 취소(§9 표 — E-Stop 아님, 거부될 수도 있음)
    robot.play(slot_map["safe.retreat"])
    kiosk.notify("접촉 감지 — 안전 동작으로 전환")
과잉주장 금지

이건 "임피던스 제어로 부드럽게 양보"가 아니라 "이상을 감지해서 다른 미리 정한 동작으로 갈아탄다"입니다. 발표에서 이 차이를 정확히 말하는 게, 안 되는 걸 된다고 했다가 질문에서 막히는 것보다 훨씬 낫습니다.

8구도 선택 — "Tracking이 아니라 Framing", 그리고 AR 가이드

연속적으로 피사체를 따라가는 서보잉은 애초에 참가자 API로 불가능합니다. 로봇을 움직여 사람을 쫓아가는 대신, 구도를 먼저 정하고 사람을 그 구도로 안내하는 쪽으로 완전히 방향을 틉니다 — 그리고 이건 화면 두 대(iPad1·iPad2)가 이미 있어서 자연스럽게 구현됩니다.

  • iPad1 — 구도 고르기(선택형으로 확장): 원래는 순수 디스플레이였지만, 여기서 가벼운 터치를 하나 추가합니다 — 팀이 참고한 "인생샷 그리드" 레퍼런스 같은 구도 템플릿 썸네일을 몇 장 보여주고(또는 로봇이 상황에 맞춰 하나를 먼저 추천 — §8-2), 사용자가 마음에 드는 걸 고르면 그 템플릿이 확정됩니다.
  • iPad2 — 실시간 AR 가이드: 확정된 템플릿의 목표 실루엣/그리드를 라이브 카메라 화면 위에 겹쳐 보여주고, 지금 사용자 위치와 얼마나 어긋났는지를 화살표·색상으로 안내합니다("반 발짝 왼쪽으로", 초록 = 정렬됨). 사용자가 스스로 위치를 맞추는 거울 역할입니다.
  • 진짜 ARKit는 안 씁니다. ARKit로 하려면 iPad에 네이티브 앱이 다시 필요해져서 §2에서 겨우 없앤 리스크가 되살아납니다. 대신 서버사이드 합성으로 같은 효과를 냅니다: Jetson이 C270 프레임에 스켈레톤·목표 그리드·정렬 화살표를 OpenCV로 그려 넣은 뒤, 그 합성 영상을 그냥 MJPEG로 iPad2 키오스크 페이지에 스트리밍합니다. 사용자 눈엔 "AR"처럼 보이지만 구현은 평범한 웹 스트리밍입니다.
  • 가벼운 모델은 계속, 무거운 모델은 한 번만: 스켈레톤 추정(예: 경량 pose 모델, TensorRT로 15~30Hz)은 인식 루프에서 매 프레임 돌려 실시간 가이드를 갱신합니다. SAM2/MobileSAM 같은 분할 모델은 훨씬 무거우므로 매 프레임 대신, 정렬 점수가 임계값을 넘긴 순간 딱 한 번만 돌려서 "실루엣이 목표 영역에 깔끔히 들어왔는지, 다른 사람이 안 끼어들었는지"를 최종 확인하는 게이트로만 씁니다.
  • 판단 루프(§5)와의 연결: 정렬 점수와 이 최종 확인 통과 여부가 §5 "구도 매칭" 노드의 입력이 됩니다. 로봇팔은 여전히 "카테고리가 바뀔 때 한 번 스냅"하는 이산적 재구도만 하고(전신→상반신처럼), 같은 카테고리 안에서 사람이 조금씩 움직이는 미세 정렬은 전부 이 AR 가이드가 사람 쪽에 맡깁니다.
파이프라인 요약

C270 프레임 → 스켈레톤 추정(실시간) → 선택된 템플릿과 오차 계산 → iPad2에 합성 영상 push → (오차가 임계값 이내로 N프레임 유지) → SAM2/MobileSAM 1회 검증 → 통과 시 §5 판단 루프가 슬롯 재생/캡처로 진행.

8-1. 게이트 확장 — 선택적 VLM 심사관 확장 지점 확정 · 구현 후순위

지금 최종 게이트(SAM2/MobileSAM)는 "실루엣이 깔끔한지, 다른 사람이 안 끼어들었는지"만 봅니다. 표정·전체 미학적 구도·손 위치처럼 기하학적 점수로는 안 잡히는 판단은 VLM 호출을 같은 자리에 하나 더 끼워 넣어서 보완합니다. 먼저 VLM 없는 로컬 검증으로 전체 기능을 완성하고, 이후 동일한 Verifier 인터페이스에 VLM을 선택적으로 연결합니다. 실시간 루프에는 절대 넣지 않고, 정렬 점수가 임계값을 넘긴 그 한 번의 순간에만 호출합니다.

게이트판단 범위속도실패/타임아웃 시
SAM2 / MobileSAM실루엣 정합, 다른 사람 끼어듦로컬, ~수백ms재시도(다음 틱)
VLM 선택적 P2표정, 전체 구도 미학, 어색한 자세클라우드 API 기준 1~3s (로컬 소형 VLM이면 더 빠름)타임아웃 시 로컬 결과만으로 진행 — VLM은 보강 게이트이며 필수 경로가 아님
지켜야 할 원칙

VLM 호출은 §4의 "빠른 일과 느린 일을 같은 함수에서 하지 않기" 규칙을 그대로 적용합니다 — 절대 판단 루프(2Hz)나 인식 루프 안에서 매 틱 부르지 않고, 딱 이 1회성 게이트에서만. 대기 시간이 발생하는 동안 iPad2에 "AI가 확인 중..." 같은 즉각적인 상태 표시를 띄워서 사용자가 아무 반응 없이 뻘쭘하게 서 있는 상황을 만들지 않는 게 SAM2 게이트를 붙일 때보다 더 중요합니다(SAM2는 로컬이라 원래도 빠름). 또한 클라우드 VLM을 쓰면 §10에 이미 있는 "현장 네트워크 확보" 리스크가 하나 더 얹히므로, 채택 실제 API 활성화 시점은 그 결정과 묶어서 판단해야 합니다. API를 붙이기 전에는 성공·거절·타임아웃 응답을 fake로 준비해 상태 전이만 먼저 검증합니다.

8-2. 첫 감지 시점 — VLM 구도 추천 멘트 확장 지점 확정 · 구현 후순위

지금 iPad1의 템플릿 추천은 규칙 기반(포즈/제품 유무 매칭)입니다. §8-1과 같은 패턴으로, §5 "사람 탐지" 노드에서 사람이 처음 잡히는 순간 딱 한 번 VLM에 프레임을 보여줘서 템플릿 추천과 함께 짧은 자연어 멘트("어울리는 소품이네요, 제품 클로즈업 어때요?")를 같이 생성해 iPad1에 띄웁니다. 규칙 기반 매칭을 먼저 완성해 전체 흐름이 VLM 없이도 굴러가게 해두고, 이후 같은 자리에 VLM을 선택적으로 연결하는 순서는 §8-1과 동일합니다 — 사용자는 추천을 그대로 안 따라도 되고 다른 템플릿으로 바꿀 수 있는 선택권은 그대로 유지합니다.

10남은 결정 — 이번 주 안에 확인 필요

항목왜 지금 정해야 하나
엔드이펙터 폰 기종 (아이폰 희망 확인)아이폰은 헤드리스 원격 셔터가 안드로이드+IP Webcam만큼 간단하지 않음. §11 트랙 C에서 오늘 짧게 검증 후 확정 — 커스텀 미니 앱 vs Pushcut 웹훅 브릿지 둘 다 시도해보고, 둘 다 안정적이지 않으면 이 장치만 안드로이드로 교체(iPad 2대는 그대로).
Jetson·iPad·폰이 같은 네트워크에 있는지키오스크 웹서버·HTTP 셔터 둘 다 로컬 Wi-Fi 전제. 현장 네트워크(핫스팟/공유기) 확보가 선행 조건 — §11 트랙 D에서 오늘 확인.
제품 인식 범위"제품을 들었다"를 어떻게 판단할지 — 손 키포인트 근접도로 단순화할지, 별도 객체 탐지를 붙일지에 따라 인식 루프 작업량이 달라짐. §8 파이프라인이 자리잡은 뒤 결정해도 늦지 않음.
음성 입력(§12) 채택 여부클라우드 API 의존(네트워크 리스크 가중)과 새 컴포넌트 추가 비용이 있어서, A/C/D 안정화 이후 시간이 남는지 보고 팀이 착수 여부·시점을 정해야 함. VLM(§8-1 게이트·§8-2 추천 멘트)은 선택적 확장 지점과 실패 정책까지 확정됐고 실제 API 활성화 시점만 후순위로 둠.

11지금 할 일 — 4개 트랙 병렬

물리 구성이 정리됐으니, 서로 거의 안 겹치는 4개 트랙으로 나눠서 오늘부터 바로 시작할 수 있습니다. 트랙 A가 제일 먼저 되어야 나머지가 실물에서 의미가 생기니 우선순위를 둔다면 A → C → D → B 순이지만, 사람이 나뉘어 있으면 넷 다 동시에 시작해도 됩니다.

트랙지금 하는 일끝나면 확인되는 것
A. 로봇 최소 왕복 phorce Studio로 슬롯 3~4개(home/전신/상반신/안전) 교시 → phorce doctor → --target sim:demo로 play() 왕복 → 실물로 같은 걸 반복 영점·부팅자세·모션 슬롯 파이프라인이 실제로 도는지. 이게 안 되면 나머지는 다 의미 없음(P0 게이트).
B. 스켈레톤 인식 로봇 없이 C270 + 노트북만으로 시작 가능. 경량 pose 모델(TensorRT 없이도 우선 OpenCV/MediaPipe로)로 키포인트 뽑고, 구도 템플릿 1개에 대한 정렬 점수 계산까지 §8 파이프라인의 핵심 로직. 로봇·iPad 없이도 통째로 선행 개발 가능한 트랙.
C. 엔드이펙터 폰 셔터 아이폰 커스텀 미니 앱(AVFoundation + 임베디드 HTTP서버)과 Pushcut 웹훅 브릿지, 둘 다 30분~1시간씩 찔러보고 더 안정적인 쪽 선택. 둘 다 애매하면 즉시 안드로이드+IP Webcam으로 전환 §10의 "이번 주 안에 확인" 항목 중 가장 일정 리스크가 큰 것 — 오늘 안에 닫아야 뒷일정이 안전함.
D. 키오스크 뼈대 FastAPI(또는 Flask)로 페이지 하나 띄우고, 두 iPad를 같은 Wi-Fi에 붙여 Safari 풀스크린(가이드 접근 모드)으로 그 페이지가 뜨는지만 확인 현장 네트워크·기기 조합에서 실제로 막히는 지점이 있는지 조기 발견. 이후 B·C의 결과물을 여기 페이지에 꽂기만 하면 됨.

12음성 입력 제안 — C270 마이크 + iPad 스피커 제안 · 미확정, 4개 트랙 밖

C270에 마이크가 내장돼 있어서, 음성으로 맥락을 듣고 iPad 스피커로 반응하는 레이어를 얹으면 키오스크 UX가 더 편해질 수 있습니다. 단, §4의 "빠른 일과 느린 일을 섞지 않기" 원칙을 어기면 사용자가 아무 반응 없이 서서 기다리는 최악의 경험이 나오므로, 처음부터 두 경로로 나눠서 설계합니다.

STT/LLM 지연을 셔터 타이밍의 임계 경로에 절대 넣지 않습니다. 실제 촬영 트리거는 지금처럼 §8의 정렬 점수(로컬·즉각)가 주도하고, 음성은 보조 신호로만 씁니다. 느린 경로는 촬영 직전이 아니라 설정/대기 단계에서만 돌려서, 지연이 있어도 사용자가 "다음 액션을 기다리는 중"이 아니라 "대화 중"인 상태가 되게 합니다. 그리고 뭔가 들었으면 처리 결과가 나오기 전에 먼저 짧은 인지 신호(iPad 스피커로 "삐" 소리나 "들었어요")부터 즉시 주고, 실제 응답은 비동기로 처리합니다 — D트랙의 기존 SSE/WebSocket 상태 push 채널에 오디오 상태(listening/processing/ready)만 얹으면 됩니다.

리스크: 해커톤 부스 현장은 주변 소음이 심할 가능성이 높아 마이크 인식 신뢰도가 §11 트랙 C(폰 셔터)만큼 리스크가 클 수 있습니다. 또한 C270 마이크 캡처는 B트랙의 영상 캡처와 별도 스레드/프로세스로 붙어야 하는 새 컴포넌트라, 채택한다면 A/C/D가 먼저 안정화된 뒤 P2로 붙이는 걸 권장합니다 — 지금 4개 트랙(§11)에는 아직 포함하지 않았습니다.
